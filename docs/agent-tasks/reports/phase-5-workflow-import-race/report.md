# Phase 5.4 Workflow import investigation

- **CI evidence:** Windows run 38163020280 copied imported workflow JSON with the expected node IDs, then all three new installed smokes observed an empty canvas snapshot. The failures were in `smoke-workflow-controls.mjs`, `smoke-workflow-widget-undo.mjs`, and `smoke-workflow-run-isolation.mjs`.
- **Likely cause:** The tests wait for Vue's graph object, which can exist before the separate desktop canvas-ready handshake finishes. The Import button was enabled during that gap, while `WorkflowWorkspace.importFile()` silently skipped the canvas-open message when `frameReady` was false. This also affects a person who imports during startup.
- **Change:** The host now retains the imported workflow for its project and opens it after canvas readiness. Imports for a prior project are discarded on project change. The three installed smokes record host readiness, visible errors, and graph node IDs if the assertion fails again.
- **Local checks:** Desktop TypeScript `tsc --noEmit` passed; `node --check` passed for all three edited smokes; `git diff --check` passed. A local packaged run of the pre-fix build preserved IDs through import, mouse wiring, Save, and Export, showing the failure is timing dependent. That run later failed in queue cancellation (`Target page, context or browser has been closed`), which is outside this import change and still needs investigation.
- **Gate:** A freshly built Windows installer must pass all three imported-workflow smokes before this fix is accepted. The new diagnostics will distinguish any remaining bridge or Vue load error from readiness timing.
