## ADR 0013: Embedded Extensions search stays on the managed engine

- **Status:** Windows installed and macOS/Linux packaged gate passed in [run 38100244801](https://github.com/vjk7989/Hyper-Studio/actions/runs/38100244801), source commit `d29dd71`.
- **Decision:** The React Workflow toolbar exposes Extensions through a parent-origin-checked canvas message. In embedded mode, the Vue Manager search gateway uses only `/hyper-studio/node-packs` on the managed loopback engine. That endpoint searches the bundled Manager catalog, including listed node names and descriptions, and only returns packs with a GitHub repository URL. Existing workflow node IDs and the reviewed install path are unchanged.
- **Reason:** The embedded layout lacked a general Manager entry point, while its inherited public search could contact Algolia or the upstream registry. A user must be able to browse extensions without an inherited cloud request or separate account.
- **Evidence:** Focused Vue gateway/bridge tests, Python catalog tests, Vue and desktop TypeScript/builds, local unpacked first-party smoke, and the fresh installed Windows smoke passed. The installed Manager dialog found a local Impact pack with no observed `api.comfy.org` or Algolia request. macOS/Linux packaged jobs passed. Graft and the codebase-memory live graph were refreshed; the latter reported 655,150 nodes and 976,907 edges, but no compressed repository artifact. This does not verify an external pack download, update/uninstall, or every Manager panel.
- **Navigation:** `frontend/views/WorkflowWorkspace.tsx` owns the button; `src/platform/distribution/hyperStudioEmbedBridge.ts` handles its message; `src/services/gateway/registrySearchGateway.ts` selects `hyperStudioLocalSearchProvider.ts`; `services/workflow/hyper_studio_pack_catalog.py` implements catalog search.

- **Decision:** Use Electron `nativeImage` for imported image dimensions and thumbnails in the main process. Preserve the existing video/ffmpeg path. Reject unreadable images explicitly.
- **Reason:** A clean installed Windows app can use Editor and hosted connections without the optional LTX Python runtime. The same unpacked Editor smoke passed 19/19 with `python` absent from `PATH` after this change.

Live model-backed generation remains outside this gate.

## ADR 0011: FCPXML media type comes from its source path

- **Status:** Fixed; installed Windows and macOS/Linux package gates passed in run 38098445173.
- **Decision:** When parsing an FCPXML resource, use its decoded `src` path to classify image/video media before the optional human-readable asset name. Keep `hasVideo=0`/`hasAudio=1` for audio-only resources.
- **Reason:** A valid package exported an image asset with the generic name `Clip`. Reimport classified it as video, attempted an ffmpeg frame extract, and failed before adding the timeline. The source path still had `.png` and correctly identifies the still image.
- **Evidence:** The Windows unpacked and installed Editor smokes passed 19 controls including SRT export, parseable FCPXML export, and reimport into a new timeline with the media clip. TypeScript, Vite, and desktop 1,483/1,483 passed. Local NSIS generation could not complete because G: ran out of disk; the Windows Actions package/install/smoke job passed and uploaded the unsigned installer artifact in run 38098445173.

## ADR 0001: Desktop editor as host

- **Status:** Managed engine, embedded canvas, and cross-mode media accepted at the Phase 4 gate.
- **Context:** The imported desktop app has the React video editor, Electron shell, and Python generation backend. The imported workflow engine has execution, with a separately packaged Vue canvas.
- **Decision:** One Electron app owns project selection, navigation, mode switch, provider setup, theme, and window identity. It starts a local workflow process for the active project and embeds a Hyper-Studio-branded Vue canvas in the same window. Editor and Workflow are modes of one project.
- **Consequence:** Electron now launches the workflow engine on loopback for the active project and serves the pinned Vue canvas via `--front-end-root`. React owns the window, toolbar, project selection, provider settings, and media panel; the embedded canvas owns graph editing. Direct engine graph execution and a Chrome iframe open/snapshot roundtrip of a 10-node workflow passed with node IDs unchanged. Packaged Electron completed a byte-identical toolbar Save/Import/Open/Export JSON roundtrip, executed a zero-model graph, and displayed its PNG in Workflow shared files and Video Editor. A distinct Editor PNG imported through the shared workspace API appeared in Workflow after a header toggle and was consumed by a `LoadImage` → `SaveImage` graph. Relaunch restored workflow bytes and nine media entries and restarted the engine/node API. A packaged local Custom HTTP mock proved an Editor job continuing through a Workflow toggle and first-party node execution with the same saved profile, producing two indexed videos; live hosted API validation and in-flight job recovery remain open. The embedded canvas installs an in-memory fallback before its module scripts because opaque iframe storage access can throw before Vue mounts. Persistent project workflows remain Electron-owned files.

## ADR 0002: Global storage and portable projects

- **Status:** Workspace foundation implemented in Phase 2; project-scoped workflow paths verified in Phase 4 packages.
- **Decision:** First run asks for one shared folder for runtimes, models, caches, and global provider settings. Each project has a chosen folder with a versioned manifest, `assets/`, `outputs/`, `workflows/`, and private metadata. Store media paths relative to the project root and validate containment. Point workflow input/output/user/database/temp paths at the active project and keep large models in shared storage. Route editor generation output to the project too.
- **Reason:** Both modes must see the same media and survive restart or transfer of the folder.
- **Implemented:** Electron creates and validates `.hyper-studio/project.json` (schema version 1) and `media.json`, plus `assets/`, `outputs/`, and `workflows/`; it writes `editor.json` when project data is saved or imported. Paths to project-owned media are stored relative to that folder. A 2-second media scan/watch updates both mode surfaces. The renderer may keep a project listing cache, but the manifest and editor file win on reopen. Legacy import is explicit and leaves source data intact.
- **Storage boundary:** Electron keeps a small private project ID-to-folder registry in user data and passes its path to Python. Python verifies registry and manifest IDs before writing tagged jobs. Generated files use project `outputs/`; a SQLite `storage_path` migration keeps queued asset references valid across restart, while legacy rows keep their prior global location. Cross-volume queued output promotion copies to a temporary file beside the destination and publishes it atomically. The backend app data and in-flight files now point to `<shared storage>/backend`; models point to `<shared storage>/models`.
- **Phase 4 path binding:** The workflow launcher maps input to project `assets/`, output to `outputs/`, user/temp/SQLite to `.hyper-studio/workflow/`, and models/cache to shared storage. A local bootstrap creates the Python environment under shared storage without downloading model packs. Project workflow JSON is listed, opened, saved, imported, and exported via typed Electron IPC; the file helper preserves raw JSON and node IDs, validates a 20 MB object and safe basename, and writes via a temporary file. Packaged toolbar Save/Import/Open/Export preserved JSON bytes in a roundtrip; relaunch reopened the project with those bytes and nine media entries.
- **Remaining limit:** Python's queue DB stores absolute project output paths; the portable project media index stores relative paths. Moving a project folder preserves indexed media, but historic queue asset links need a rebind/migration. Packaged smoke proved both directions of media use, including an imported Editor PNG as a `LoadImage` graph input. `ProjectContext.tsx` now applies mode changes to current project state, avoiding an autosave overwrite from a stale render. The media scanner excludes generated `_big/_small_thumbnail.png` derivatives when their source exists, preventing the thumbnail loop seen in packaged smoke.

## ADR 0003: One credential and job boundary

- **Status:** Implemented as a mocked, code-level Phase 3 slice; live provider access is unverified.
- **Decision:** Global named provider profiles hold URL, model, and secret references; the renderer receives non-secret metadata only. A broker accepts project/profile/model per job, snapshots submitted configuration, limits concurrency per profile, normalizes state/output, and registers finished media. Provide LTX, Runway, Google Veo, fal.ai video, and mapped Custom HTTP adapters. The same registry powers Editor generation and first-party workflow nodes.
- **Security:** Use a secure local store outside project manifests, workflow JSON, renderer state, and logs. Ask before importing legacy LTX/fal/Gemini credentials. Keep third-party nodes' credential handling separate. A custom URL requires request/auth/output mapping; localhost alone does not imply video generation support.
- **Boundary:** Hosted API calls belong in the desktop integration boundary. The imported workflow engine's `AGENTS.md` bars outbound internet behavior in its core.
- **Implemented:** Electron stores named LTX, Runway, Veo, fal.ai, and Custom HTTP profiles in an encrypted vault. OS encryption is used when available; a passphrase vault is available otherwise. Renderer IPC exposes redacted metadata, model choices, configuration checks, and explicit confirmed import of legacy keys. Old backend key setters return 410 and new settings writes scrub key fields. The old API Keys tab routes to Connections. Electron's broker snapshots a profile per submission, limits each profile to two active jobs, permits different profiles to run concurrently, emits normalized job changes, and registers successful outputs in project media. Adapters cover direct and asynchronous contracts. A random-token authenticated loopback bridge gives first-party workflow nodes the same broker without serializing the token into workflow JSON.
- **Limits:** The broker is in-memory: restart recovery of active jobs is absent. Cancel aborts local polling/download but cannot guarantee a remote provider stops; the UI says “Stop tracking.” The current generic Editor/Workflow and Home composer covers text-to-video. Specialized Editor/feature forms still use project-scoped local Python routes. Live API credentials, local image uploads, and remote cancellation are not smoke-tested. The Phase 4 launcher passes the bridge URL/token to the managed workflow process; a packaged local-mock job proved the first-party node can use the same saved profile as Editor. That mock does not verify hosted provider acceptance.

## ADR 0006: Trust boundary for project output routing

- **Status:** Implemented for current Editor generation routes in Phase 2.
- **Decision:** Renderer requests carry only `projectId`. Electron main creates a private registry and gives its path to Python through `HYPER_STUDIO_PROJECT_REGISTRY`. Python resolves a tagged request only when the registry entry and `.hyper-studio/project.json` agree, and ensures `outputs/` remains inside the selected project. Unknown or invalid IDs fail with 422. Untagged legacy requests retain their old output path.
- **Scope:** Direct video/image/retake/extend/IC-LoRA routes and queued video features accept `projectId`. The desktop media scanner registers completed files in the relative project index. The backend does not write `media.json`, avoiding two writers for one JSON file.
- **Consequence:** The global SQLite queue remains for local job history while generated files live in project folders. The current watcher polls every 2 seconds; live UI updates can lag by that interval. Hosted-provider broker jobs currently live in Electron memory and need restart recovery.

## ADR 0007: Embedded workflow frame trust boundary

- **Status:** Implemented and checked in packaged Windows and macOS canvas smokes; Windows local-mock workflow execution and Linux zero-model execution passed.
- **Context:** The packaged Electron page and loopback workflow server have different origins. The upstream server rejects cross-site iframe requests, while broad frame exemptions would expose the local process to unrelated websites.
- **Decision:** Electron permits workflow navigation and frame headers only for the active engine's exact origin. The launcher passes a random per-process embed token to the server. The server admits a cross-site request only when it is a `GET` iframe navigation carrying that token; other cross-site requests keep their 403 path. Vue's opaque iframe storage fallback is embedded-only and runs before module scripts.
- **Evidence:** Packaged Projects → Workflow rendered `#graph-canvas`. An unrelated cross-site iframe request returned 403. Preserve exact-origin and token checks when changing window, CSP, or engine startup code.

## ADR 0008: Managed workflow account and node-catalog boundary

- **Status:** Managed cloud boundary, final7 installed Windows compatibility/settings and local-fixture Manager install, and macOS/Linux packaged checks passed; live provider and external third-party install behavior remain unverified.
- **Decision:** Embedded Workflow must not request the upstream account, registry, cloud proxy, billing, or telemetry as part of ordinary project use. Account and billing dialogs, settings panels, user routes, and cloud-only template entries are hidden or blocked in the embedded distribution. The desktop host owns credentials and provider jobs. Retain upstream technical node IDs in imported JSON so missing nodes remain identifiable.
- **Cloud policy:** Managed projects do not register the 43 inherited account-proxy node modules. Relative account-proxy URLs and explicit `comfy.org` hosts are rejected before a network session; managed CSP and connectivity checks omit the upstream origin. The first-party `HyperStudioGenerateVideo` node still calls the authenticated local broker. This does not block an explicitly reviewed third-party pack's own network behavior after installation.
- **Local catalog:** `GET /hyper-studio/node-packs?id=<pack-id>` reads the installed manager's bundled `custom-node-list.json` without updating or querying the upstream registry. It returns only requested IDs (at most 100; string IDs of 1–128 characters). The Vue client accepts entries with a GitHub repository URL, shows missing-pack guidance, and routes install through an explicit source-review confirmation. The manager receives local/default/nightly coordinates only after confirmation. If manager metadata is absent or a pack is not listed, the result is empty; this is not a general package search or automatic install.
- **Evidence and limits:** Focused managed-cloud Python checks passed 10/10; upstream compatibility checks passed 65 with 2 skipped; desktop provider adapter and server/CSP checks each passed 8/8. Local Vue node-pack tests passed 32/32; an earlier five-file embedded-account suite passed 79/79. Final7 Windows install preserved three workflow variants and node IDs 37, 90909, and 91001, exposed missing-node guidance, and passed a real Manager queue/install/restart using a repository-local ImpactInt fixture. The test redirects the exact reviewed Impact Pack Git URL to that fixture and blocks other HTTP clones; it confirms manager mechanics and node registration, not installation of the external Impact Pack. Host Open/Import waits for GraphCanvas tab restoration after restart (`f66fa25`). Installed Settings showed Hyper-Studio, hid account/pricing controls, and passed the dark “Nodes 2.0” heading contrast threshold; the inspected post-restart canvas also showed legible dark Overview/favorites, minimap controls, and Run toolbar count. The packaged Workflow smoke observed no account button or upstream Comfy/LTX cloud request. macOS/Linux package-smoke and brand-audit jobs passed. Live hosted credentials and macOS/Linux installer installation/uninstall remain unverified.

## ADR 0009: Project removal is an Electron transaction

- **Status:** Project lifecycle and scoped Windows installed controls passed on final5; macOS/Linux package smokes passed in [run 38093974210](https://github.com/vjk7989/Hyper-Studio/actions/runs/38093974210). Wider feature/release audit remains open.
- **Decision:** The app offers app-only removal and OS Trash from both Recent projects and Projects through one dialog. Electron owns both actions. It blocks active jobs, closes the workspace and managed engine, and clears its project record, recent entry, and folder registries only after the requested action succeeds. App-only removal leaves project files intact and Open project folder can restore the same manifest/project ID. Trash requires a matching managed manifest and rejects the shared storage root, drive roots, symlink/junction paths, and a folder containing another registered project. Legacy folders without a managed manifest offer app-only removal.
- **Reason:** A renderer-only delete would leave private folder registries behind or lose a project after a failed Trash operation. Explicit choices and a full-path confirmation reduce accidental loss.
- **Evidence:** Final5 installed lifecycle smoke passed create/rename/reopen, app-only remove/restore, simulated Trash failure with record preservation, real OS Trash of a disposable folder, and restart persistence. A held loopback provider job blocked both removal choices without losing files. Focused main-process tests cover the guards. The final5 unsigned installer passed project, Editor, Workflow, provider, Manager, and package smokes with local fixtures. The embedded Workflow conflict scan now avoids an idle upstream Registry bulk lookup after a local pack install while retaining local import-failure analysis (focused Vue 12/12). macOS and Linux packaged smoke and brand audit passed in run 38093974210. See `docs/gates/project-controls-windows.md` for exact limits; broader Editor/Workflow feature and installer installation/uninstall gates remain open.
